# Hermes 다중 에이전트 운영 구조

## 목적

Discord에서 요청을 받는 Hermes를 단순 명령형 챗봇이 아니라, 작업을 분해하고 전문 에이전트에 위임한 뒤 결과를 검증하는 총괄 에이전트로 운영한다.

## 구성

| 역할 | 책임 | 상태 변경 범위 |
| --- | --- | --- |
| `default` | 요청 분해, 위임, 결과 검증, 최종 보고 | 승인된 작업만 위임 |
| `dbcollector` | 기존 독립 브라우저 4개와 수집 감독기 관리 | 수집 승인 범위만 |
| `dbreviewer` | 연락처 품질, 중복 제거, 신규 이메일, 엑셀 검수 | Notion 쓰기 금지 |
| `notionloader` | 드라이런, 10건 파일럿, 승인된 전체 적재 | 단계별 승인 필수 |
| `reporter` | 대시보드와 실행 결과를 읽어 보고 | 읽기 전용 |

동시에 실행할 수 있는 하위 작업은 4개로 제한한다. 장기 작업은 `growthhigh-db` Kanban 보드에 역할별로 배정한다.

## 실행 흐름

```text
Discord 요청
  -> default가 목표·기준시점·승인 여부 확인
  -> 독립 작업을 역할별 하위 에이전트에 위임
  -> 하위 에이전트가 결과와 근거 반환
  -> default가 건수·파일·실행 상태를 재검증
  -> 하나의 결과로 통합 보고
```

## 승인 경계

- 새 원본 수집 시작, 수집 일시정지·재개는 명시적 승인 후 실행한다.
- 검수 승인, Notion 10건 파일럿, 전체 적재는 각각 별도로 승인받는다.
- CAPTCHA는 자동 우회하지 않고 사람의 조치가 필요한 상태로 보고한다.
- 연락처 값은 메시지 본문에 나열하지 않고 승인된 파일로만 전달한다.

## 완료 기준

요청 접수나 `started: true`만으로 완료 처리하지 않는다. 작업 번호 또는 실행 번호, 최종 건수, 실패·보류 건수와 검증 결과가 확인돼야 완료다.

## 2026-09-23 검증

- Discord 총괄 프로필의 하위 작업 위임 기능 활성화
- 전문 프로필 4개 구성
- 두 하위 작업의 병렬 실행 및 결과 회수 확인
- `reporter` 전용 Kanban 작업 실행 완료 확인
- 하위 프로필에 메시징 자격정보가 복제되지 않음을 확인
- 게이트웨이 재시작 후 구성 점검 통과

운영 자격정보와 내부 실행 식별자는 보안상 이 공개 저장소에 기록하지 않는다.
